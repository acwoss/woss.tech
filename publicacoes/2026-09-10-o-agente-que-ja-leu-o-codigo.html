O agente que já leu o código


    

      Toda sessão nova de um agente de IA começa como um desenvolvedor no
      primeiro dia. Um grafo de código persistente é o que faz a segunda
      sessão herdar o que a primeira aprendeu.
    

  






  


  


    

      Um agente de IA não tem véspera. Cada sessão nova abre com a mesma
      ignorância da primeira: não sabe onde mora a autenticação, não sabe que
      aquele módulo com nome de utilitário é o coração do domínio, não sabe
      que o arquivo de 6 mil linhas só delega. Para trocar três linhas ele
      precisa antes reconstruir o mapa — e reconstruir o mapa
      é grep, ler arquivo inteiro, seguir import, ler outro
      arquivo inteiro.
    


    

      É exatamente o que faz um desenvolvedor no primeiro dia. A diferença é
      que o desenvolvedor faz isso uma vez e depois carrega o mapa na cabeça
      por anos. O agente faz de novo. Toda sessão. E paga em contexto — o
      recurso do qual ele precisa justamente para raciocinar sobre a mudança.
    


    

      O Codebase
      Memory MCP ataca esse ponto: ele indexa o repositório num
      grafo de conhecimento persistente em SQLite e o expõe
      por MCP. A sessão de amanhã pergunta ao grafo o que a sessão de hoje
      teve de descobrir lendo arquivo. Este texto é o que eu medi
      usando-o.1
    


    
Quanto custa reaprender


    

      Número vale mais que analogia, então escolhi uma pergunta concreta num
      repositório público que qualquer leitor pode baixar: como o
      FastAPI resolve dependências — quem chama solve_dependencies
      e o que ela chama? É a pergunta típica de quem vai mexer em
      injeção de dependência e não conhece o projeto.
    


    

      O repositório é o fastapi/fastapi no commit
      50113da: 1.138 arquivos .py, 112.998 linhas de
      Python. Indexar levou 8,80 s e produziu
      31.130 nós e 73.526 arestas.2
    


    

    

      A rota do grafo são duas chamadas. A primeira acha o símbolo e já diz a
      faixa de linhas exata:
    


    

    

      A segunda percorre o grafo nas duas direções e devolve, em 3.146 bytes,
      72 callees agrupados por módulo com a distância em saltos, mais
      os 3 callers. É a resposta que o grep não dá em
      nenhuma quantidade de linhas: quem chama é uma
      pergunta sobre arestas, não sobre texto.

      São 86 vezes menos bytes para uma resposta mais
      completa. E a comparação é generosa com o grep: contei apenas
      três arquivos, quando os 72 callees se espalham por 22 módulos
      e utils.py sozinho tem 27 linhas de import para
      resolver.
    


    

      
nota de método

      

        Comparei bytes de saída, não tokens medidos
        com um tokenizer. A conversão de 4 bytes por token é
        a mesma razão que a própria ferramenta usa como teto ao dimensionar
        resposta, e serve para ordem de grandeza — não para dois dígitos de
        precisão. O comando de cada linha está nas notas.
      

    


    
O que o grafo guarda


    

      Um call graph honesto não sai de expressão regular. Ele exige
      saber que user.profile.display_name() resolve para
      Profile.display_name, declarado três módulos adiante — e
      isso é informação de tipo, não de sintaxe. O projeto
      resolve isso com duas passadas.
    


    

    

      A primeira passada é tree-sitter, com as gramáticas compiladas
      dentro do binário, e é puramente sintática. A segunda — que o projeto
      chama de Hybrid LSP — é uma implementação enxuta em C de
      algoritmos de resolução de tipo, inspirada nos language servers
      de cada linguagem, e refina as arestas de chamada. Ela existe para
      Python, TypeScript, PHP, C#, Go, C, C++, Java, Kotlin, Rust e Perl;
      as demais linguagens ficam na resolução textual.
    


    

      O resultado é um grafo com rótulos e tipos de aresta explícitos. Este é
      o censo real do FastAPI indexado, em 3.930 bytes de
      get_architecture — o equivalente a chegar num projeto e
      alguém desenhar o mapa no quadro:
    


    

    

      Essa separação merece ênfase porque é onde a maioria das ferramentas
      mente. CALLS é chamada com alvo resolvido;
      CALL_REFERENCE é callable passado como valor com
      alvo único; USAGE é identificador usado sem alvo provado.
      Além disso há HTTP_CALLS ligando chamada a rota entre
      serviços, DATA_FLOWS mapeando argumento para parâmetro,
      SIMILAR_TO por MinHash para quase-clone. As
      consultas saem por um subconjunto de leitura de openCypher,
      então detectar código morto é uma linha:
    


    

    
As três memórias


    

      Chamar tudo isso de "memória" esconde que são três coisas com
      durabilidades diferentes. Vale separar, porque a segunda é a que de fato
      ensina um agente ao seguinte — e é a que quase ninguém usa.
    


    

      

        
          
memóriao que guardasobrevive a

        
        
          
o grafoestrutura derivada do código: símbolos, chamadas, rotassessão e reinício da máquina

          
o ADR (manage_adr)o que o código não diz: decisão, trade-off, armadilhasessão, e é o único que não se regenera

          
o artefato .zsto grafo comprimido, versionado ao lado do fontea máquina — atravessa o time

        
      

    


    

      O grafo é derivado: apagar o cache não perde nada além
      de tempo de CPU. O ADR não. Ele é um documento em markdown por
      projeto, com seções nomeadas, que um agente escreve e o próximo lê. É
      literalmente o recado que o desenvolvedor que está saindo deixa para o
      que está chegando:
    


    

    

      
o README está à frente do binário

      

        O README do main documenta
        mode='set_sections', que reescreve só as seções nomeadas.
        Na v0.10.8, que é a que está instalada aqui, esse
        argumento é recusado com "the sections argument is not an update
        primitive and has been removed" e nenhuma escrita
        acontece. Só update funciona, e ele
        substitui o documento inteiro — leia com
        get antes de escrever, ou você apaga o recado de outra
        sessão.
      

    


    

      A terceira memória é a que atravessa pessoas. Ao indexar com
      persistence ligado, o grafo é exportado para
      .codebase-memory/graph.db.zst, ao lado do fonte. Quem clona
      o repositório importa o artefato e roda indexação incremental só do
      próprio diff, em vez de reindexar tudo. No FastAPI o artefato
      ficou em 5,9 MB, contra 70,5 MB de banco local — e o
      artifact.json ao lado registra o commit exato de
      que ele saiu, o que é o que impede alguém de confiar num grafo de três
      meses atrás.
    


    

    
Instalar e usar


    

      É um executável nativo único, sem runtime de linguagem, sem
      serviço, sem chave de API. O instalador detecta os agentes já presentes
      na máquina e escreve a configuração de MCP de cada um — na v0.10.8 ele
      declara 43 superfícies de cliente:
    


    

    

      Preferindo configurar à mão, é uma entrada de MCP como qualquer outra.
      No Claude Code, em ~/.claude.json ou no
      .mcp.json do projeto:
    


    

    

      Depois é reiniciar o agente e dizer "indexe este projeto". Mas
      há um detalhe que muda o resultado: por padrão o artefato de
      time não é escrito. Se você quer a terceira memória, tem de
      pedir:
    


    

    

      A ordem de uso que economiza mais é sempre a mesma:
      get_architecture para se orientar,
      search_graph para descobrir o nome exato,
      trace_path para as relações, e
      get_code_snippet só no fim, quando já se sabe qual são as
      146 linhas que importam. Ler arquivo continua sendo necessário —
      depois de saber qual.
    


    
O que isso custa


    

      Nada disso é grátis, e três custos aparecem rápido.
    


    

      Disco. 31.130 nós do FastAPI ocupam 70,5 MB de SQLite —
      mais de dez vezes o artefato comprimido. Aqui na minha máquina há 97
      projetos indexados e o cache está em 4,5 GB. É
      descartável, mas não é pouco.
    


    

      Frescor. Um grafo de ontem responde com confiança sobre
      código que mudou hoje, e essa é a falha mais perigosa da ideia toda —
      ela não parece uma falha. O projeto trata isso com um observador em
      segundo plano, com detect_changes mapeando o diff
      não comitado para os símbolos afetados, e com
      check_index_coverage, que diz quais arquivos o indexador
      não cobriu inteiro. A ressalva importa: cobertura
      limpa significa "nenhuma lacuna registrada", não prova de
      completude. Afirmação de ausência — "não há mais nenhum chamador" —
      continua exigindo grep.
    


    

      Histórico do Git. Se você comitar o artefato, comite com
      cadência. Ele é reescrito a cada indexação, o Git guarda cada reescrita
      como um blob novo inteiro, e o próprio projeto documenta um time
      que chegou a ~6 GB em ~350 commits desse único caminho. Um
      marco, uma release, um job noturno — não cada
      salvamento.
    


    

      Feita a conta, ainda fecha. O grafo de um monólito que eu indexei no
      trabalho tem 167.902 nós e 765.371 arestas; nenhuma janela de contexto
      comporta esse repositório, e nunca vai comportar. A pergunta não é se o
      agente cabe no código — é se ele chega na sessão sabendo onde procurar.
      É a mesma coisa que a gente pede de um desenvolvedor novo: não que ele
      tenha lido tudo, mas que não comece do zero toda segunda-feira.
